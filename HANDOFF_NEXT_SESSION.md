## Architecture & patterns established — don't relitigate these

- **Schema + pure-engine split, for anything AI-generates.** A Pydantic model for internal validation, a separately hand-rolled raw JSON-schema dict for what Claude tool-calling / Gemini's `responseSchema` actually see (never `model_json_schema()` — Gemini's schema support has real, previously-hit gaps), and a **pure, network-free, unit-testable expansion function** that turns AI-authored semantic content into fully-resolved render data. This is the shape of `motion_schema.py`/`motion_engine.py` and `mind_map_schema.py`/`mind_map_engine.py` both. Follow it for anything new in this family.
- **Gemini schema gotchas, hard-won, don't reintroduce:** `type` must never be an array/union — use a sibling `"nullable": true` instead (broke Motion Studio in production once already). Recursive/self-referencing schemas (`$ref`) are unverified against a live Gemini call from this sandbox (`generativelanguage.googleapis.com` isn't reachable) — Mind Map v2's tree schema deliberately unrolls into 4 fixed explicit levels rather than gambling on recursion support. There's a permanent structural test (`TestGenerationSchemaStructure` in `test_mind_map_engine.py`, and equivalent coverage in `test_motion_engine.py`) that walks the schema tree checking for both mistakes — extend it, don't bypass it, if you add new schemas.
- **Three-path credential model, reused everywhere:** BYOK header / server-key-with-its-own-quota / manual-paste-mode. Each AI feature (cards, Motion Studio, Mind Map v2) has its own quota pool but shares the credential-resolution pattern and the `X-Client-Id` anonymous device identifier.
- **Byte-sync requirement:** any prompt that exists in both `api/index.py` (Python) and a JS mirror (`motion-api.js`, `mind-map-doc-api.js`) must be re-verified byte-identical after every edit using the documented process — extract Python's output with a placeholder, splice into the JS template literal via a script (never hand-retype), diff the two. Both Motion Studio's and Mind Map v2's manual prompts follow this.
- **Few-shot examples matter more than more rules.** Applied to Motion Studio's prompt this session (richer 6-layer worked example replacing a trivial one-layer example) and built into Mind Map v2's prompt from the start. If you're improving any generation prompt's quality, a fully worked, schema-validated example is the highest-leverage lever, confirmed twice now.
- **`expand_script()`/`expand_mind_map()` must run before anything reaches the player.** The player (`motion-player.js`) expects fully-resolved keyframes, not the AI-authored shorthand (`at`/`hold`/`style` on emphasis layers, etc.). Feeding it raw source data doesn't error — it just renders wrong (this was hit directly this session; see "recurring lessons" below).
- **`UPCOMING_FEATURES.md` gets updated in the same commit as any real change.** Hard project convention, followed all session, don't break it under time pressure (it was broken once this session under real time pressure and had to be fixed retroactively — see the commit log).
- **PAT hygiene:** John provides a PAT per chat and has explicitly said he wants to **reuse the same one across an entire session** for velocity — his call to make, but the standard "still one-time-use, still worth rotating" guidance is worth restating plainly the first time it comes up in a new chat, then not repeated every single push after that (repeating it constantly becomes noise, not safety). Embed in the remote URL only for the actual push, scrub back to plain HTTPS immediately after, check `git log HEAD..origin/main --oneline` before every push to catch drift.
- **Verification discipline, the actual house style, not just a suggestion:** unit tests with real assertions; live HTTP requests against a running local server; Playwright screenshots for anything visual, driven through the *real* app's actual navigation where possible, not only an isolated seeding harness; pixel-level canvas inspection (not just "a screenshot looked fine") when confirming an animation actually renders; re-viewing a file after any edit that touches HTML/JSX-like template strings, since a `str_replace` succeeding doesn't guarantee valid resulting nesting (caught a real stray `</ol>` bug this exact way). This has caught a genuinely large number of real bugs this session — see the log below. Don't skip steps under time pressure; it's cheaper to verify than to ship broken and find out from a screenshot.

## The Encarta identity pivot — an active, ongoing initiative, decided, don't relitigate the direction

### How this started

John shared four documents in one message:
1. A **cinematic 60–75s motion-graphics brand-film script** ("Your Quiet Companion") — particle systems, volumetric glow/bloom, a professional voiceover, composed ambient music with heartbeat pulses, 3D card flips, bioluminescent map visuals.
2. A **"Lernin vs. Encarta: A Design Archaeology Report"** — a large, well-researched document (verified accurate against the real codebase on spot-checks — it quotes `sound.js`'s exact frequencies and an exact code comment correctly) proposing a big grab-bag of Encarta-inspired changes: MIDI-style app-identity sound, ambient map drones, thematic per-deck sounds, a hidden "MindMaze"-style quiz game, literal Easter eggs (a hidden pineapple, a "good boy" search trigger), TTS narration, camera fly-to transitions, seasonal map themes, "Map Treks," a generative per-deck color tint, a font swap to Literata, and a "content over chrome" visual decluttering pass.
3. A document that reads as **another AI's critique of this session's actual Help/onboarding work** — accurate on some points (the onboarding canvas being hardcoded dark against a light app is real; no skip control is a real gap), slightly off on others (assumed the video autoplays; it's actually opt-in via a poster button) — and proposed adding real audio hooks to `motion-player.js` with example code, per-deck dynamic onboarding generation, and tap-to-skip interactivity.
4. An **"Encarta vs. Lernin" positioning essay** — more strategic/philosophical (reference-vs-retention, browse-vs-drill, editorial-authority-vs-generative-personalization) than actionable, useful as framing rather than a task list.

### The assistant's assessment (given directly, not held back)

- **Document 1 (the cinematic script) is not buildable with the current engine, and this was verified against the actual code, not assumed:** `motion_schema.py`'s own module docstring explicitly states *"No particles, physics, audio-reactive, or beat detection."* There is zero audio capability anywhere in the pipeline (grepped to confirm), no particle system (40-layer schema cap, vs. hundreds of points a particle system needs), no glow/blur/gradient rendering (flat 2D canvas context, no `shadowBlur` usage anywhere), no true 3D. This describes a professionally produced brand film — a different *kind* of project (video production with a sound designer and voice actor), not a Motion Studio script. This assessment was given plainly rather than attempting a watered-down version and calling it done.
- **Documents 2–4's grab-bag was sorted into three buckets:** small/real/low-risk (theme-aware onboarding canvas, a skip control, decluttering chrome, camera fly-to), genuinely new capability requiring deliberate commitment (real audio in Motion Studio, per-deck dynamic onboarding generation, TTS), and things the assistant would actively push back on as literally described (MIDI earworm chime as literally an "app identity sound," a literal transplanted pineapple/dog Easter egg, "Quiz Trek" territory-unlocking gamification specifically because it risks incentivizing gaming FSRS's honest-grading principle rather than genuine retrieval practice).
- **The central tension named explicitly:** Encarta-style playful nostalgia (hidden jokes, a game layer, earworm sound branding) versus the calm/safe-haven "we've suffered old habits too, here's the rescue" voice just established in the Help rewrite. This was framed as a real strategic fork, not something to silently pick a side on.

### The decision

**John chose: lean into playful Encarta nostalgia — sound identity, easter eggs, a game layer.** Not the calm-only direction, and not a no-unifying-theme cherry-pick. This is a deliberate, explicit call from the product owner. Per established working style, **do not re-litigate this** — the tension was named once, heard, and decided. The job now is executing it well, including still exercising judgment on individual implementation choices within that direction (e.g., the FSRS-honesty concern about gamified territory-unlocking is worth keeping in mind for *that specific feature* if/when it's built, without re-opening the overall direction question).

### The tension, and how it resolved in practice so far

The one easter egg built this session (see Phase 1 below) shows a workable synthesis: it's *playful* (a hidden response to typing a greeting instead of a search) but *also* written in the exact same warm companion voice as the rest of the app ("Hi. We're here. Search whenever you're ready — no rush.") rather than being disconnected whimsy. The recommendation going forward: playful discovery moments that *reinforce* the companion framing rather than random non-sequiturs. Both directions can coexist if execution stays deliberate about this — it doesn't have to be either/or, but it does mean every piece needs the same care this first one got, not just "add a quirky thing because Encarta had one."

## Recurring lessons this session, worth internalizing

- **Verify uncommitted state explicitly before writing a handoff or trusting a summary of "what's done."** This session's own context got trimmed mid-way through, and real, good, already-built work sat uncommitted and un-narrated for several turns until a plain `git status --short` surfaced it. Don't assume your own prior narration is complete — check the filesystem.
- **A synthetic Playwright `.click()` doesn't always reproduce what a real tap does.** The Help TOC bug was invisible to a synthetic click on the anchor (didn't trigger the browser's native hash-navigation the same way) but was immediately reproducible by directly setting `location.hash` and watching the view change. When a click-based test passes but something still feels off, try the more direct mechanism before concluding there's no bug.
- **`str_replace` succeeding doesn't mean the resulting HTML is valid.** A new closing paragraph landed between two `</ol>` tags this session — caught only by re-viewing the file after the edit, not by the tool reporting success.
- **Feeding a player raw, unexpanded AI-schema data (with shorthand like `at`/`hold`/`style`) doesn't error — it just renders wrong.** Always run generation-schema content through the real expansion step (`expand_script()`/`expand_mind_map()`, or the actual live endpoint) before it reaches `motion-player.js` or an equivalent renderer.
- **When a design-review document makes a claim about the current implementation, check it before accepting it.** One such document this session got several things right (verified by direct code inspection — it clearly had real repo access) but also got one detail wrong (assumed autoplay when the video was actually opt-in). Useful input either way, but "another AI/document said so" isn't itself verification.
- **A repulsion-only physics simulation with no radius awareness can look fine at a small test scale and still be fundamentally broken at real scale.** The card mind map's overlap bug had nothing to do with node count scaling the tuned constants — it was that repulsion never had any concept of actual rendered node size. Test at the scale that will actually happen (a 97-card deck, not just a 25-node synthetic graph), and re-verify tuned constants when you find a new failure mode rather than assuming the earlier verification still covers it.

## Working style, confirmed and reinforced this session

- Terse confirmations ("Continue," "Yes," "Keep going") mean proceed autonomously.
- Direct recommendations for technical/execution calls; genuine strategic/product forks (the Encarta identity direction was the biggest one this session) get named plainly and left for an explicit decision — then, once decided, not re-litigated.
- Every commit gets a real, detailed message: what was broken/missing, what changed, how it was verified. This has been the standard all session and should continue.
- `UPCOMING_FEATURES.md` updated in the same pass as any real change — including retroactively fixing the one time this slipped under time pressure.
- When feedback is critical ("looks like a slideshow," "wrong voice"), take it at face value and rebuild rather than defending the original — both the motion graphic and the Help voice got meaningfully better from being rebuilt, not patched.

## Tools & resources, as used this session

- **Local backend:** `cd api && MOTION_SERVER_CLAUDE_KEY="dummy-for-local-test" python3 -m uvicorn index:app --port 8125` (or any free port) — must be started in the *same* tool call as whatever depends on it; background processes don't survive across separate sandbox tool invocations.
- **Static + API proxy for full-stack Playwright testing:** a small custom `static_proxy.py` (serves `public/` statically via `SimpleHTTPRequestHandler`, forwards `/api/*` to the uvicorn backend) — rewritten ad hoc each time this session, worth keeping a copy of if this becomes a recurring need again.
- **Playwright:** confirmed reliable throughout (Chromium at `/opt/pw-browsers`). Used for: seeding real IndexedDB data via the app's actual `db.js` functions and rendering the real component; driving the *real* app through actual clicks/navigation (not just an isolated harness) when verifying router/UI-wiring behavior specifically; pixel-level canvas inspection via `getImageData` when confirming an animation genuinely renders content, not just that controls appear.
- **`fake-indexeddb`** (`npm install fake-indexeddb --no-save`, not a real dependency) for Node-level testing of `db.js` functions without a browser.
- **Throwaway test harnesses** (bare HTML files calling real app modules directly) are useful and were used extensively this session, but should be deleted before committing — they're scaffolding, not shipped product, unlike `motion-test.html` which is a deliberate permanent dev tool.
- **PAT for this session** was explicitly reused across every push per John's stated preference — remains his call each new chat, worth a brief, non-repeated mention of the one-time-use norm the first time it comes up.
